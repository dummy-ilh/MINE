# Chapter 22: Exploration-Exploitation — Contextual Bandits (LinUCB, Thompson Sampling)

## 1. Intuition

Chapter 20 previewed exploration as a cold-start tool; Chapter 21 flagged the rich-get-richer feedback loop. This chapter formalizes the underlying tension precisely: at every recommendation decision, the system faces a choice between **exploitation** (show the item the current model is most confident will perform well) and **exploration** (show an item with uncertain but potentially higher value, specifically to learn its true value). Pure exploitation, applied forever, is exactly what causes Chapter 21's feedback loops — the model never learns whether an under-shown item might actually be great, because it's never shown enough to find out.

**Contextual bandits** are the standard formal framework for managing this trade-off systematically, rather than ad hoc. "Bandit" comes from the multi-armed bandit problem (a gambler choosing among slot machines with unknown payout rates); "contextual" means the decision also depends on side information (the user/context), which is exactly the recsys setting.

## 2. The Contextual Bandit Setup

At each round (each recommendation request): observe context $x$ (user features, session context), choose an action $a$ (which item to recommend) from the available action set, observe a reward $r$ (click, engagement — the implicit feedback signal from Ch. 1). The goal is to learn a policy that maximizes cumulative reward over time, which requires **balancing exploitation of the current best-known action against exploration of uncertain actions that might be even better.**

This differs from the standard supervised learning setting used throughout most of this curriculum (Chapters 5-15) in one crucial way: in supervised learning, you passively observe (context, action, reward) triples generated by *someone else's* (or the current production system's) policy; in a bandit setting, **your own policy's choices determine what data you observe next** — if you never try action $a$, you never learn its reward, no matter how good it might secretly be. This is the formal version of the exposure-bias problem flagged repeatedly since Chapter 6.

## 3. LinUCB — Upper Confidence Bound Approach

LinUCB assumes the expected reward for action (item) $a$ given context $x$ is linear in the context features: $\mathbb{E}[r|x,a] = x^T\theta_a$, where $\theta_a$ is a per-item (or per-item-cluster) parameter vector learned from observed data (this is a ridge-regression-style linear model, one per action).

The core idea — **Upper Confidence Bound (UCB)**: rather than just picking the action with the highest *estimated* reward, pick the action with the highest **upper bound** of a confidence interval around that estimate:

$$a_t = \arg\max_a \left(x_t^T\hat\theta_a + \alpha\sqrt{x_t^T A_a^{-1}x_t}\right)$$

- $x_t^T\hat\theta_a$: the point estimate of expected reward (exploitation term).
- $\alpha\sqrt{x_t^T A_a^{-1}x_t}$: an uncertainty bonus (exploration term) — $A_a$ is a matrix (roughly, $X^TX$ accumulated from past observations of action $a$) whose inverse quantifies how *little* data has been collected for this action in this region of context space. The less data, the larger this term, the more the action's total score is boosted by uncertainty.
- $\alpha$: a tunable hyperparameter controlling how aggressively to explore (larger $\alpha$ → more exploration weight).

**The key behavior this produces**: an item with a mediocre point estimate but very little supporting data (large uncertainty term) can still win the argmax over an item with a slightly higher point estimate but lots of supporting data (small uncertainty term, since $A_a^{-1}$ shrinks as more data accumulates for that action) — this is precisely the mechanism that lets promising-but-under-explored items (Chapter 20's cold-start items, exactly) get selected some of the time, systematically, rather than being permanently starved by pure exploitation.

## 4. Thompson Sampling — Bayesian Approach

Thompson Sampling takes a different, sampling-based approach: maintain a **posterior distribution** over each action's expected reward (e.g., a Beta distribution for click-through-rate-style binary rewards, or a Gaussian for continuous rewards), and at each round, **sample** one value from each action's posterior, then pick the action with the highest sampled value.

$$\tilde{r}_a \sim P(r_a \mid \text{observed data for } a), \quad a_t = \arg\max_a \tilde{r}_a$$

**Why this naturally balances exploration and exploitation**: an action with a narrow, confident posterior (lots of data) will nearly always sample close to its true mean — so it wins the argmax reliably when its mean is genuinely high, and loses reliably when its mean is genuinely low. An action with a wide, uncertain posterior (little data) will occasionally sample a very high value purely by chance (due to its wide variance) — giving it a real, calibrated chance of being selected precisely in proportion to how *plausible* it is that its true value is actually the best, given current uncertainty. This is a more elegant, automatically-calibrated exploration mechanism than LinUCB's explicit tunable bonus term ($\alpha$), though it requires maintaining and sampling from an actual posterior distribution per action rather than a simpler point-estimate-plus-bonus computation.

## 5. Worked Numerical Example — Comparing Item Selection

Two candidate items for a user, with observed historical data:

**Item X**: shown 1,000 times, 100 clicks → estimated CTR $\hat{p}_X = 0.10$, narrow confidence (lots of data).
**Item Y**: shown 10 times, 2 clicks → estimated CTR $\hat{p}_Y = 0.20$, wide confidence (very little data).

**Pure exploitation** (greedy, always pick highest point estimate): picks Item Y every time (0.20 > 0.10) — but this estimate is based on only 10 observations, extremely noisy; the true CTR could easily be much lower (or, to be fair, could also be genuinely higher) than 0.20.

**Thompson Sampling intuition** (using Beta posteriors, Beta(successes+1, failures+1) as a simple illustration): Item X's posterior is Beta(101, 901) — narrowly concentrated around 0.10, standard deviation roughly $\sqrt{\frac{101\times901}{1002^2\times1003}} \approx 0.0095$ (about 1%). Item Y's posterior is Beta(3, 9) — mean 0.25, but with a standard deviation of roughly $\sqrt{\frac{3\times9}{12^2\times13}}\approx0.123$ (about 12%) — over 10x wider. On any given sampling round, Item Y's sampled value could reasonably land anywhere from roughly 0.05 to 0.5+, sometimes below Item X's typical sampled range and sometimes well above it — meaning Item Y gets selected a meaningful fraction of the time (proportional to genuine uncertainty about whether its true CTR beats Item X's), while Item X gets selected the rest of the time reliably around its confident 0.10 estimate. This produces a **principled, automatically-calibrated exploration rate** — neither "always trust the noisy small-sample winner" (pure exploitation) nor "ignore promising small-sample items entirely" (no exploration at all).

## 6. Production Considerations

- Contextual bandits are commonly used specifically at the **candidate/slot allocation level within re-ranking** (Ch. 16, 21) — e.g., deciding how many of the final list's slots to allocate to "confident, well-established" items versus "promising but under-explored" items, rather than replacing the entire ranking model.
- LinUCB's linear-reward assumption is a real limitation — production systems often use non-linear reward models (e.g., a neural network) combined with an approximate uncertainty-estimation technique (e.g., ensemble-based or dropout-based uncertainty), since real recsys reward functions are rarely well-approximated by a simple linear model over raw features.
- Thompson Sampling's Bayesian framing integrates naturally with the multi-objective/business-tension themes recurring in this module — the "prior" can be informed by business priors (e.g., a genuine belief that new content deserves a fair, if limited, chance), making it a natural fit for the exploration-for-cold-start use case (Ch. 20) specifically.
- Both approaches require careful monitoring of the **exploration cost** — the short-term relevance/engagement hit taken by showing uncertain items — and this cost is exactly what needs to be weighed against long-term value in an A/B test (foreshadowing Ch. 24's discussion of network effects and long-run metrics in bandit-influenced systems).

## 7. Interview Traps

- Proposing a purely greedy/exploitation-only recommendation policy without acknowledging that this systematically starves under-explored items of the data needed to ever prove their worth — exactly Chapter 21's feedback-loop failure mode reappearing at the decision-policy level.
- Confusing LinUCB's uncertainty bonus with Thompson Sampling's posterior sampling as though they're the same mechanism — they achieve similar goals (balancing point estimate against uncertainty) via genuinely different mathematical approaches (an explicit additive confidence bound vs. sampling from a full posterior distribution).
- Not being able to explain *why* less data for an action leads to more exploration of that action in either method — the mechanism (larger $A_a^{-1}$ term in LinUCB; wider, more spread-out posterior in Thompson Sampling) needs to be stated concretely, not just asserted.
- Ignoring that bandits are typically applied at a specific, bounded scope (slot allocation within re-ranking) rather than replacing the entire recommendation pipeline — overstating the bandit framework's role in the overall system architecture.

## 8. L5-Differentiating Talking Points

- Explain precisely why passively-collected data creates exposure bias in a way that active bandit-style data collection directly addresses — connecting this chapter back to the exposure bias concern first raised in Chapter 6 and echoed in Chapter 21's feedback-loop discussion, showing a throughline across the whole curriculum.
- Contrast LinUCB and Thompson Sampling on genuine practical trade-offs (LinUCB's simpler, deterministic confidence-bound computation vs. Thompson Sampling's more elegant but computationally heavier posterior-sampling requirement) rather than treating them as interchangeable "bandit algorithms."
- Explicitly scope where bandits fit in the broader system (slot allocation within re-ranking, Ch. 16/21) rather than presenting them as a wholesale alternative to the entire ranking pipeline — showing precise systems-architecture placement.
- Name the exploration cost explicitly as a quantifiable trade-off that should be measured and bounded (not left as an unconstrained, open-ended cost) — showing engineering discipline around a technique that could otherwise degrade short-term user experience if applied carelessly.
