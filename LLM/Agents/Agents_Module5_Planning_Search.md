# Agents Module 5 — Planning & Search: Tree-of-Thought, MCTS, Reflexion (Master Notes, Expanded)

## 0. Why go beyond ReAct — the limitation this module addresses

ReAct (Module 4) interleaves reasoning and acting, but it's fundamentally **a single linear path** — at every Thought-Action step, the model commits to one reasoning direction and moves forward; there's no mechanism to explore multiple alternative reasoning branches, compare them, and backtrack if a branch turns out to be worse than another. For problems with a genuine **branching decision space** (multiple plausible next steps, where some lead to dead ends and others to solutions — puzzles, planning problems, complex multi-step math), committing to a single linear path can get irreversibly stuck exactly where a human problem-solver would naturally backtrack and try a different branch. This module covers techniques that add **explicit branching, evaluation, and backtracking** on top of the reasoning process itself.

---

## 1. Tree-of-Thought (ToT)

### The core idea, in plain words
Instead of generating one linear reasoning chain (CoT/ReAct), **explicitly represent the reasoning process as a tree**: each node is a partial reasoning state (a "thought" — an intermediate step toward solving the problem), and each node can branch into **multiple candidate next thoughts**, generated by prompting the model to propose several different possible next steps rather than just one. The tree is then searched (not every branch explored exhaustively — see search strategies below) to find a path to a solution, with the ability to **abandon a branch and backtrack** if it's evaluated as unpromising.

### The four components ToT formalizes (worth being able to name all four)
1. **Thought decomposition**: how to break the reasoning process into discrete "thought" units small enough to be individually generated and evaluated, but large enough to represent meaningful reasoning progress (this granularity choice is itself a design decision, task-dependent).
2. **Thought generation**: given a partial reasoning state (a node), generate multiple candidate next thoughts — either by sampling the model multiple times independently at that node (get diverse candidates via temperature sampling, LLM Basics Module 6), or by prompting the model once to explicitly propose several distinct next steps in one generation.
3. **State evaluation**: assess how promising a given partial reasoning state/node is — either by prompting the model itself to self-evaluate ("does this partial solution look on track? rate 1-10" or "is this state: sure / maybe / impossible"), or via a simpler heuristic/deterministic check when the task allows one (e.g., in a math puzzle, checking whether a partial numeric result has already exceeded the target, making it provably impossible to reach the target from here).
4. **Search algorithm**: how to actually traverse the tree given the branching and evaluation — commonly **breadth-first search (BFS)** (explore all nodes at the current depth, keep the top-b most promising before expanding to the next depth — this is structurally identical to beam search from LLM Basics Module 6, just applied to reasoning-thought nodes instead of token sequences) or **depth-first search (DFS) with backtracking** (go deep along the most promising branch, but backtrack to try a sibling branch if the current path is evaluated as a dead end).

### Concrete illustration — Game of 24 (the canonical ToT paper example)
Task: given 4 numbers (e.g., 4, 9, 10, 13), combine them using +, -, ×, ÷ to reach exactly 24.

- **Thought generation at the root**: propose several different first operations, e.g. "13-9=4 (left: 4,4,10)", "10-4=6 (left: 6,9,13)", "9+4=13 (left: 10,13,13)" — multiple distinct branches from the same starting state.
- **State evaluation**: for each resulting partial state, the model (or a simple heuristic) assesses whether it still looks plausible to reach 24 from the remaining numbers — a state like "left: 4,4,10" might be judged more promising than "left: 10,13,13" if the model recognizes 4×4+10 doesn't reach 24 but flags a nearby profitable combination, versus a state judged "impossible" gets pruned immediately, no further generation wasted on that branch.
- **Search**: BFS keeps, say, the top-5 most promising partial states at each depth, expanding only those — rather than exhaustively generating every possible operation sequence (which would explode combinatorially) or committing to just one linear guess (which could get stuck exactly as a single ReAct trace could).

**Why this matters over plain CoT/ReAct for this kind of task**: a single linear CoT chain making an early wrong operation choice has **no way to recover** — it just continues down a doomed path to an incorrect final answer. ToT's explicit backtracking/pruning means a bad branch's cost is limited to however deep it was explored before being pruned, not the entire remaining reasoning chain.

## 2. Monte Carlo Tree Search (MCTS) applied to LLM reasoning

### Classical MCTS (the four-phase loop, from game-playing AI — worth knowing this originates from systems like AlphaGo)
1. **Selection**: starting at the root, repeatedly choose child nodes according to a selection policy that balances **exploitation** (favor nodes with a high average evaluated value so far) and **exploration** (favor nodes that haven't been visited/explored much yet) — classically formalized via the **UCB1 (Upper Confidence Bound)** formula:
```
UCB1 = average_value(node) + C × sqrt( ln(parent_visits) / node_visits )
```
   - The first term rewards nodes that have historically scored well (exploitation).
   - The second term grows larger for nodes visited less often relative to their parent (exploration bonus) — as `node_visits` stays small while `parent_visits` grows, this term stays large, pulling search back toward under-explored options periodically rather than always greedily re-selecting the current best-looking node.
   - `C` is a tunable constant controlling the exploration/exploitation balance.
2. **Expansion**: once selection reaches a node that hasn't been fully expanded, generate one or more new child nodes (in the LLM setting: prompt the model to generate a candidate next reasoning step/thought from this state).
3. **Simulation (rollout)**: from the newly expanded node, run forward to some terminal/evaluable state — in classical game-playing MCTS this is often a fast random playout to the end of the game; in LLM-reasoning adaptations, this is typically the model itself generating a full plausible continuation quickly (perhaps with a smaller/faster model, or a shorter/greedier generation) to estimate how promising this branch is, without the full cost of careful step-by-step exploration.
4. **Backpropagation**: propagate the result/value obtained from the simulation **back up through every node visited during selection**, updating each node's average value and visit count — this is what makes the `average_value` term in UCB1 meaningful for future selection decisions; the whole cycle then repeats (many iterations) before finally committing to the actual next real step based on which child had the most/best-evaluated visits.

### Why MCTS adds value over plain ToT's BFS/DFS
ToT's BFS/DFS relies on a single evaluation pass per state to decide what to keep/prune. MCTS instead builds up a **statistically averaged** estimate of each branch's promise through repeated simulation and backpropagation — better suited to noisy evaluation signals (a single LLM self-evaluation of "is this state promising" can be unreliable/inconsistent; averaging over multiple simulated rollouts smooths out that noise), at the cost of substantially more total generation calls (each simulation is itself a rollout requiring model generations) — a real compute-cost tradeoff to name explicitly if asked to compare MCTS vs. ToT-BFS for LLM reasoning.

### Numerical intuition for the exploration-exploitation tradeoff
Suppose after some search, node A has average value 0.7 from 20 visits, and node B has average value 0.6 from 2 visits, with parent visits = 25, C=1.0:
```
UCB1(A) = 0.7 + 1.0 × sqrt(ln(25)/20) = 0.7 + sqrt(3.219/20) = 0.7 + sqrt(0.161) ≈ 0.7 + 0.401 = 1.101
UCB1(B) = 0.6 + 1.0 × sqrt(ln(25)/2)  = 0.6 + sqrt(3.219/2)  = 0.6 + sqrt(1.610) ≈ 0.6 + 1.269 = 1.869
```
Despite B's lower average value, its much smaller visit count gives it a large exploration bonus, making UCB1(B) > UCB1(A) — MCTS would select B next, to gather more information about whether it's actually better than its limited 2-visit sample suggests, rather than purely exploiting A's currently-higher average. This is the concrete mechanism worth being able to reproduce if asked "why doesn't MCTS just always pick the node with the best average value so far."

## 3. Reflexion — self-critique as "verbal reinforcement learning"

### The core idea
Rather than (or in addition to) branching/searching over multiple reasoning paths, **Reflexion has the agent critique its own prior attempt after a failure, generate an explicit natural-language reflection about what went wrong, and store that reflection in context/memory for its next attempt** — described by its authors as a form of **"verbal reinforcement learning"**: instead of updating numeric weights via gradient descent based on a reward signal (actual RL), the "learning signal" is a **piece of self-generated natural-language critique**, which is then included as additional context on the retry, influencing behavior purely through in-context conditioning (LLM Basics Module 4's ICL mechanism) rather than any weight update.

### The loop, step by step
1. Agent attempts the task (via ReAct or similar).
2. An evaluator (could be the environment itself — e.g., a failed test suite, LLM Basics Module 8's external-verification concept — or the model self-evaluating) determines the attempt failed, and ideally *why*.
3. The agent generates an explicit **verbal reflection**: a natural-language explanation of what went wrong and what to try differently ("I incorrectly assumed X; next time I should verify X before proceeding" — genuinely analogous to a human debugging their own reasoning after a mistake).
4. This reflection is stored (appended to context, or written to an external memory store — directly connects to Module 6's memory-systems material) and **included in the context for the next attempt** at the same or a related task.
5. Repeat until success or a max-attempt cap (Module 1's stopping condition, applied at the level of whole task attempts rather than individual loop iterations).

### Why this is meaningfully different from just "retry and hope"
A naive retry with no reflection re-attempts the task with **no new information** — if the model's original mistake stemmed from a systematic reasoning error (not just unlucky sampling), a bare retry (even at a different temperature/sample) has no particular reason to avoid the same mistake. Reflexion's explicit verbal critique **directly targets the specific failure mode identified**, giving the next attempt genuinely new, relevant context to condition on — this is the same core principle as self-consistency (Module 3) and ReAct (Module 4): **grounding subsequent reasoning in real, specific information (here, a diagnosed failure reason) beats relying on the model's undifferentiated prior tendencies alone.**

## 4. When search-based planning is worth the extra compute — the decision framework

This is the practical, "when would you actually deploy this" synthesis question:

- **Plain CoT/ReAct** is sufficient when the task is largely linear/sequential with low branching complexity, and errors (when they happen) aren't typically the result of a genuinely wrong high-level approach that needed comparing against alternatives.
- **Tree-of-Thought** is worth the extra compute when the task has a **real combinatorial branching structure** where multiple plausible next steps exist and some lead to dead ends (puzzles, certain planning/search problems) — the extra compute buys the ability to compare alternatives and backtrack, which a linear method structurally cannot do.
- **MCTS** is worth the additional cost over ToT specifically when **state evaluation is noisy/unreliable** and would benefit from being statistically averaged over multiple simulated rollouts rather than trusted from a single evaluation pass — a strictly higher-compute, higher-reliability option for the hardest branching problems.
- **Reflexion** is worth adding when the task allows **multiple full attempts** (not just multiple branches within one attempt) and there's a way to detect failure and reasonably diagnose its cause (either from an external verifier or the model's own retrospective analysis) — particularly valuable for tasks with a clear pass/fail signal (code that must pass tests) where iterative self-correction across attempts is natural.

**One line to have ready for a system-design-style question**: "The general principle across all of these is: the more genuine branching/backtracking structure and the noisier the per-step evaluation signal a task has, the more the extra compute of tree search or repeated-attempt reflection pays for itself — for simpler, more linear tasks, that extra compute is largely wasted and plain ReAct is both cheaper and sufficient."

| | Plain CoT/ReAct | Tree-of-Thought | MCTS (LLM-adapted) | Reflexion |
|---|---|---|---|---|
| Structure | Single linear path | Explicit tree, multiple branches | Tree + statistical averaging via simulation | Single path, but repeated across multiple full attempts |

## 6. Quick-fire Q&A (self-test)

**Q: What specific limitation of ReAct does Tree-of-Thought address?**
A: ReAct commits to a single linear reasoning/action path with no mechanism to explore alternative branches or backtrack — for tasks with genuine branching decision structure, an early wrong choice can't be recovered from. ToT explicitly represents reasoning as a tree with multiple candidate next-thoughts per node, evaluates states, and can prune/abandon unpromising branches.

**Q: Name and briefly explain all four components ToT formalizes.**
A: Thought decomposition (choosing the granularity of a reasoning "unit"), thought generation (producing multiple candidate next thoughts from a state), state evaluation (assessing how promising a partial state is), and search algorithm (BFS or DFS-with-backtracking to traverse the tree given the branching and evaluations).

**Q: Write the UCB1 formula and explain what each term controls.**
A: `UCB1 = average_value(node) + C × sqrt(ln(parent_visits)/node_visits)`. The first term rewards nodes with historically high average value (exploitation); the second term grows larger for less-visited nodes relative to their parent, providing an exploration bonus that prevents the search from purely greedily exploiting the current best-looking option; C tunes the balance between the two.

**Q: Why might MCTS outperform ToT's single-pass BFS/DFS evaluation for LLM reasoning, and what's the cost tradeoff?**
A: MCTS builds a statistically averaged value estimate for each branch through repeated simulation and backpropagation, which smooths out noise from any single unreliable LLM self-evaluation — better suited when per-state evaluation is inconsistent. The tradeoff is substantially higher compute cost, since each MCTS iteration requires additional simulated rollouts beyond a single evaluation call.

**Q: What does "verbal reinforcement learning" mean in the context of Reflexion, and how is it different from actual RL (e.g., PPO from LLM Basics)?**
A: Reflexion generates a natural-language self-critique after a failed attempt and includes it as context for the next attempt, influencing future behavior purely through in-context conditioning — not through any gradient-based weight update. Actual RL (PPO) updates the model's weights based on a numeric reward signal; Reflexion's "learning" happens entirely within the prompt/context across attempts, with the underlying model weights staying completely frozen.

**Q: Give the general decision principle for when the extra compute of tree search or Reflexion-style reflection is worth it.**
A: The more a task has genuine branching/backtracking structure (multiple plausible paths, some leading to dead ends) and the noisier its per-step evaluation signal, the more tree-search or repeated-attempt reflection compute pays for itself; for simpler, more linear tasks with reliable per-step correctness, that extra compute is largely wasted and plain ReAct is both cheaper and sufficient.
