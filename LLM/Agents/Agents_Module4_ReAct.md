# Agents Module 4 — ReAct: Reasoning + Acting (Master Notes, Expanded)

## 0. The gap ReAct fills — connecting Modules 2 and 3

Module 2 gave the agent the ability to act (tool calls). Module 3 gave the agent better reasoning (CoT). The naive way to combine them is **"reason fully first, then act"** — generate a complete CoT reasoning chain, then decide on and execute an action. **ReAct's actual contribution is showing that this naive combination is worse than interleaving reasoning and acting at a fine grain** — alternating single reasoning steps with single actions and their real observations, rather than batching all the reasoning up front.

---

## 1. The ReAct loop, structurally

ReAct (Yao et al., 2022, "ReAct: Synergizing Reasoning and Acting in Language Models") structures each loop iteration as three explicit, labeled parts generated by the model:

```
Thought: <the model's reasoning about what it currently knows and what to do next>
Action: <a tool call, or a final-answer action>
Observation: <the real result returned by executing the action — NOT generated by the model>
```

This triple repeats — Thought → Action → Observation → Thought → Action → Observation → ... — until a final-answer Action is emitted (directly reusing Module 1's stopping-condition mechanism).

**Critical detail to state precisely**: the "Observation" line is **not generated by the LLM** — it's inserted into the context by the surrounding agent framework, after actually executing the Action (exactly the tool-execution loop from Module 2). If you're asked to write out an example ReAct trace, get this right: the model generates Thought and Action; the framework/environment generates Observation; then the model generates the *next* Thought, now conditioned on that real Observation text.

### Concrete worked example
Task: "What's the population of the capital of the country where the Eiffel Tower is located?"

```
Thought: I need to find where the Eiffel Tower is located first.
Action: search("Eiffel Tower location")
Observation: The Eiffel Tower is located in Paris, France.
Thought: The Eiffel Tower is in France, and Paris is already the capital, so I need Paris's population.
Action: search("population of Paris")
Observation: Paris has a population of approximately 2.1 million (city proper).
Thought: I now have the answer.
Action: finish("The population of Paris, the capital of France, is approximately 2.1 million.")
```

Notice the second Thought **directly reuses the real Observation text** ("Eiffel Tower is in Paris, France") to correctly recognize that Paris is already the capital (no separate "find the capital of France" step was needed) — this is the interleaving benefit in action: the reasoning at each step is grounded in a genuinely-retrieved fact, not a guess, and the model can adapt its plan based on what it actually learns, not what it assumed it would learn.

## 2. Why interleaving beats "reason fully, then act" — the actual mechanism

### The core problem with reason-then-act
If the model generates its **entire** reasoning chain before taking any action, every step of that reasoning chain is conditioned only on the model's **prior beliefs/guesses**, not on any real information gathered along the way — the model might correctly plan "step 1: look up X, step 2: use X to compute Y, step 3: use Y to answer," but it cannot *verify or adjust* that plan based on what X actually turns out to be, since no action has been taken yet by the time the reasoning chain is fully written. If the model's initial assumption about what X would be turns out to be wrong once actually retrieved, a reason-then-act system has already committed to a downstream plan built on the wrong assumption.

### Why interleaving fixes this — directly reusing Module 1's error-recovery framing
ReAct's Thought-Action-Observation interleaving means **each new Thought is generated with the real, current Observation already in context** — so the model's plan can be revised at every single step based on actual retrieved information, not just its own prior guess. This is exactly Module 1's "agentic loops enable error recovery" principle, now applied specifically to the reasoning/planning process itself, not just to task-level action sequencing: **ReAct lets reasoning be grounded and re-grounded at every step, rather than being a single, ungrounded, upfront plan.**

### Numerical framing (same compounding-error lens used throughout this syllabus)
Suppose a 3-hop retrieval task (like the Eiffel Tower example, extended to 3 real lookups) has each individual lookup+reasoning step succeed with 80% probability **when grounded in the actual previous observation** (interleaved), vs. only 55% probability **when the plan for all 3 hops is committed upfront based on assumptions about what earlier lookups will return** (reason-then-act, since a wrong assumption early on cascades into a wrong plan for later steps that can't be corrected once written):
```
Interleaved (ReAct):     0.8^3 = 51.2% end-to-end success
Reason-then-act (upfront plan): 0.55^3 = 16.6% end-to-end success
```
This concretely illustrates why the *empirical* ReAct paper results (interleaving reliably outperforming both pure CoT and pure act-only baselines on multi-hop QA and decision-making benchmarks) make sense mechanistically, not just as an observed empirical fact to memorize.

## 3. Comparison to "Act-only" (tool use with no explicit reasoning trace)

The other naive baseline ReAct improves on is **acting without any explicit intermediate reasoning** — the model just emits actions directly based on the task and observations, with no "Thought" text generated in between. ReAct's ablations show this also underperforms full interleaving — **the explicit Thought text isn't just cosmetic**; it gives the model a place to explicitly reason about *why* the next action makes sense given the current observation, catching potential mistakes (e.g., "wait, this observation doesn't actually answer what I need — I should search for something more specific instead") before committing to a possibly-wrong next action. This directly reuses Module 3's mechanistic point about CoT: explicit reasoning tokens provide genuine extra sequential computation the model can condition subsequent tokens on, whereas jumping straight to an action compresses that reasoning into the model's fixed-depth, single-pass computation with no externalized checkpoint.

## 4. Failure modes specific to ReAct-style agents

### Hallucinated observations
A subtle but serious failure mode: if the agent framework has any bug or ambiguity in how it distinguishes model-generated text from injected observation text, the model can sometimes **generate its own fake "Observation" line** (since it has, after all, seen many real Observation-formatted lines in its context/training and can pattern-match the format) rather than waiting for the framework to supply a real one — effectively hallucinating a tool result instead of actually calling the tool. **Mitigation**: the agent framework must strictly control generation (e.g., stop the model's generation immediately after it emits an Action, before it has a chance to generate a fake Observation itself, then programmatically append the real Observation before resuming generation) — this is a concrete engineering discipline point worth naming if asked about production reliability, not just an abstract accuracy concern.

### Loop divergence / getting stuck
An agent can enter a repetitive cycle — e.g., repeatedly searching for slight variations of the same unhelpful query, never making progress, without any built-in signal that it's stuck. This connects directly to Module 1's stopping-condition discussion: a max-iteration cap is the blunt safety net, but better mitigations include detecting **repeated near-identical actions** (if the last 2-3 actions are essentially the same, that's a strong signal to force a different approach or escalate/give up) and explicitly prompting the model to notice and reason about lack of progress, not just naively continuing the Thought-Action-Observation cycle indefinitely.

### Compounding hallucination in Thoughts
If an early Thought contains a subtly incorrect inference (even though grounded in a real Observation, the model's *interpretation* of that observation can still be wrong), later Thoughts built on that same flawed interpretation can compound the error — interleaving with real observations helps a lot (per Section 2's math) but doesn't fully eliminate this risk, since the model's *reasoning about* an observation is still a generative, fallible process, not a guaranteed-correct one. This is why Module 8 (evaluating agents) and techniques like Reflexion (Module 5, self-critique loops) exist as further mitigations layered on top of ReAct itself.

## 5. Side-by-side summary table (memorize this cold)

| | Reason-then-Act | Act-only | ReAct (interleaved) |
|---|---|---|---|
| When reasoning happens | Fully upfront, before any action | Never explicit | Interleaved, one step at a time, after each real observation |
| Can adapt plan based on real retrieved info mid-task? | No — plan is committed before any action | Implicitly, but no explicit reasoning trace to catch mistakes | Yes — this is the core benefit |
| Risk of compounding early wrong assumptions | High | Moderate (no explicit reasoning to catch errors, but at least grounded in real observations) | Lower (grounded + explicit reasoning at every step) |
| Explicit checkpoint to catch a bad next-action choice | No | No | Yes (the Thought step) |

## 6. Quick-fire Q&A (self-test)

**Q: Write out the three-part structure of a single ReAct loop iteration, and state precisely which parts are model-generated vs. framework-generated.**
A: Thought (model-generated reasoning) → Action (model-generated tool call or final answer) → Observation (framework-generated, the real result of executing the action — never generated by the model itself).

**Q: Why does reason-then-act underperform ReAct's interleaving, mechanistically?**
A: In reason-then-act, the entire multi-step plan is committed based on the model's prior assumptions before any real information is gathered, so if an early assumption turns out wrong once actually retrieved, the downstream plan built on it can't be corrected — it was already fully written. Interleaving lets each new Thought condition on the real, current Observation, allowing the plan to be revised at every step based on actual retrieved information rather than upfront guesses.

**Q: Why does act-only (no explicit Thought) underperform full ReAct, even though both use real observations?**
A: The explicit Thought step gives the model a place to genuinely reason about whether the current observation actually supports the next intended action, catching potential mistakes before committing to a possibly-wrong action — omitting it compresses that reasoning into the model's fixed-depth single-pass computation with no externalized checkpoint, the same mechanistic argument as CoT's benefit over direct-answer generation.

**Q: What is "hallucinated observation" as a ReAct failure mode, and what's the concrete engineering mitigation?**
A: The model generating its own fake Observation-formatted text instead of waiting for the framework to supply a real tool result, since it has seen the Observation format many times and can pattern-match it. Mitigation: the framework must strictly halt model generation immediately after an Action is emitted, programmatically supply the real Observation, then resume generation — never letting the model's own generation continue uninterrupted past an Action.

**Q: Does interleaving with real observations fully eliminate compounding reasoning errors? Why or why not?**
A: No — while grounding each Thought in a real Observation substantially reduces compounding error risk compared to ungrounded upfront planning, the model's *interpretation* of a correct observation can still itself be a subtly wrong, fallible generative inference, and later Thoughts built on that flawed interpretation can still compound the mistake. This is part of the motivation for further techniques like Reflexion/self-critique layered on top of ReAct.
