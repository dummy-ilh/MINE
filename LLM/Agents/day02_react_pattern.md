# Day 2: The ReAct Pattern (Reasoning + Acting)

## 1. The Intuition First

Think about how *you* solve an unfamiliar problem — say, "Is my flight tomorrow going to be delayed?"

You don't silently think through the entire answer and then act once. You interleave:

> *"I should check the weather at the departure airport." → [you check] → "Okay it's clear there, but let me check the destination too." → [you check] → "Also clear. Let me check if the airline has any current advisories." → [you check] → "No advisories. Based on all this, I think the flight is fine."*

Notice the pattern: **think a little → act → observe the result → think again, informed by what you just saw → act again → ... → final answer.**

That interleaving — not planning everything up front, not acting blindly without reasoning — is exactly what **ReAct (Reason + Act)** formalizes for LLM agents. It was introduced specifically because two earlier approaches each had a critical flaw:

- **Reasoning-only (Chain-of-Thought)**: the model "thinks out loud" but never touches the real world — so if its internal knowledge is wrong or outdated, it just reasons itself confidently into a wrong answer. No way to course-correct with real data.
- **Acting-only**: the model calls tools but doesn't verbalize *why* — so when a tool call fails or returns something unexpected, there's no reasoning trace to fall back on or debug, and the model can't adapt its strategy based on intermediate results.

ReAct fuses them: **every action is preceded by an explicit thought, and every thought is informed by the previous action's real-world observation.**

---

## 2. Formalizing It

### 2.1 The Loop Structure

```
Thought_1 → Action_1 → Observation_1 →
Thought_2 → Action_2 → Observation_2 →
...
Thought_n → Final Answer
```

Each **Thought** is free-text reasoning generated by the LLM (not executed — just reasoning).
Each **Action** is a structured call to a tool (search, calculator, API, code execution).
Each **Observation** is the real, external result of that action, injected back into the context.

This is literally just: *put the model in a loop, and force it to explain its reasoning at each step before acting.*

### 2.2 Why the "Thought" Step Isn't Just Fluff

It's tempting to think the "Thought" text is just for human readability. It's not — it does real computational work:

1. **It decomposes the problem** — turns "answer this complex question" into "what's the next single fact I need?"
2. **It creates an error-correction checkpoint** — if Observation_2 contradicts what Thought_1 assumed, Thought_2 can explicitly say "that's not what I expected, let me try a different approach."
3. **It biases the next token generation** — because the model just "wrote down" its plan, the subsequent Action tokens are conditioned on that plan, making the tool call far more likely to be well-formed and relevant (this is the same mechanism that makes chain-of-thought improve accuracy on math problems — reasoning tokens change the conditional distribution over the next tokens).

## 3. Worked Example: Full Trace, Step by Step

**Task**: "What is the population of the birth city of the director of the movie *Oppenheimer*?"

This is a **multi-hop question** — deliberately chosen because it cannot be answered in a single retrieval step, which is exactly the case ReAct is built for.

**Available tools**: `search(query)` → returns short text snippet.

Let's trace it exactly as the LLM would generate it, turn by turn.

---

**Turn 1**
```
Thought: I need to find who directed Oppenheimer before I can find their birth city.
Action: search("director of Oppenheimer 2023 movie")
Observation: "Oppenheimer (2023) was directed by Christopher Nolan."
```

**Turn 2**
```
Thought: Now I know the director is Christopher Nolan. I need his birth city next.
Action: search("Christopher Nolan birth city")
Observation: "Christopher Nolan was born in London, England."
```

**Turn 3**
```
Thought: Now I need the population of London.
Action: search("population of London")
Observation: "As of 2023, the population of London is approximately 8.87 million."
```

**Turn 4**
```
Thought: I now have all the facts I need: director = Christopher Nolan, birth city = London, population ≈ 8.87 million. I can answer.
Final Answer: The population of London, the birth city of Christopher Nolan (director of Oppenheimer), is approximately 8.87 million.
```

---

### 3.1 What Just Happened, Mechanically

Look at what made this work — each Thought did something a single-shot LLM call *cannot* do:

- **Turn 1's thought** decomposed an unanswerable one-shot question ("population of birth city of director of X") into a *first sub-question* the model could actually resolve with one search call.
- **Turn 2's thought** *used the observation from Turn 1* ("Christopher Nolan") to form the next query. A non-agentic system would have had to hardcode "first search director, then search birth city" — here the model itself chained the dependency.
- **Turn 3's thought** did the same again — chaining on "London" learned only from Turn 2.
- **Turn 4's thought** recognized the stopping condition: *"I now have all the facts I need"* — the model decided, on its own, that the loop was complete. Nobody hardcoded "3 searches then stop."

If you tried to solve this with a single LLM call and no tools, the model would have to already know Nolan's birth city and London's exact population from training data — and if either fact were outdated or the model misremembered, there'd be no way to catch it. ReAct grounds every hop in a fresh, verifiable observation.

## 4. Worked Example #2: When ReAct Catches Its Own Mistake

This is the part interviewers really want to see you understand — **ReAct's real power is error recovery mid-trajectory**, not just multi-hop chaining.

**Task**: "What's the current CEO of the company that makes the ChatGPT app?"

```
Thought: The company that makes ChatGPT is OpenAI. I need to find OpenAI's current CEO.
Action: search("OpenAI CEO")
Observation: "Sam Altman briefly stepped down as CEO of OpenAI in November 2023 before returning days later."

Thought: This observation is about a past event (Nov 2023) and is ambiguous about who is CEO *right now*. I should search again with a more specific, current-focused query.
Action: search("OpenAI CEO 2026 current")
Observation: "As of 2026, Sam Altman is CEO of OpenAI."

Thought: Now I have an unambiguous, current answer.
Final Answer: Sam Altman is the current CEO of OpenAI, which makes the ChatGPT app.
```

Notice: the second Thought is doing something a fixed pipeline structurally *cannot* do — it looked at its own observation, judged it as **insufficient/ambiguous**, and **decided to retry with a refined action**. This self-correction loop is the single biggest practical reason ReAct-style agents outperform single-shot RAG or fixed pipelines on real-world tasks: **the reasoning step is what lets the agent notice when it's wrong.**

## 5. Production Considerations

### 5.1 Cost of the Thought Tokens

Every Thought is extra generated tokens, on every single turn. For an n-turn trajectory, you're paying for n reasoning traces in addition to the actions themselves. Compare:
- Single-shot LLM call: ~1 generation.
- ReAct with 4 turns: ~4 generations, each including reasoning text, roughly doubling the total output tokens versus action-only agents (like pure function-calling loops with no explicit thought).

**Mitigation used in production**: many frameworks now let you keep the reasoning *internal* (not shown to the user, sometimes even hidden from the persisted context after the turn completes) to reduce both cost and prompt-injection surface — but you almost never remove it from generation entirely, because removing it measurably hurts action quality.

### 5.2 The Infinite Loop / Runaway Cost Failure Mode

Because the model decides when to stop (Turn 4 above: *"I now have all the facts I need"*), a poorly grounded model or a bad prompt can fail to ever reach that conclusion:

```
Thought: I should double check this.
Action: search("population of London")
Observation: "approximately 8.87 million."
Thought: Let me verify this from another source to be sure.
Action: search("London population verify")
Observation: "approximately 8.8 million."
Thought: These numbers are slightly different, let me check again...
```

This is a **real, commonly-cited production incident pattern** — agents looping dozens of times, burning tool calls and tokens, without ever satisfying their own internal "am I done" check.

**Standard production mitigations** (interview-relevant, memorize these):
1. **Max iteration cap** — hard stop after N turns (e.g., 10), forcing a "best effort" final answer.
2. **Explicit stopping criteria in the system prompt** — e.g., "If you've confirmed a fact from 1 reliable source, that is sufficient; do not re-verify."
3. **Step budget / cost budget passed into the prompt** — telling the model how many actions it has left, so its own reasoning can factor in urgency ("I only have 1 action left, I should answer now").
4. **Repetition/loop detection** — programmatically detect if the last k actions are near-duplicates and force termination or escalate to a human.

### 5.3 Latency

Each Thought→Action→Observation round trip is a full LLM inference call. A 5-turn ReAct trajectory has **5x the latency** of a single-shot call (plus tool execution time on top). This is why ReAct is rarely used for latency-sensitive user-facing paths (e.g., live chat first-token response) without either streaming intermediate output or falling back to a cached/simpler path.

## 6. Common Interview Trap: ReAct vs. Plain Chain-of-Thought vs. Plain Function-Calling

Interviewers love to test whether you can tell these apart precisely.

| Pattern | Reasons? | Acts on real world? | Loops based on observations? |
|---|---|---|---|
| Chain-of-Thought (CoT) | ✅ | ❌ | ❌ |
| Plain function-calling (no explicit thought) | ❌ (implicit at best) | ✅ | ✅ (sometimes) |
| **ReAct** | ✅ | ✅ | ✅ |

**Interview-ready distinction**: *"Function-calling loops can technically loop and act, but without an explicit reasoning step, the model doesn't verbalize why it's choosing an action — which makes error recovery weaker and debugging harder. ReAct's core contribution is forcing an explicit reasoning trace before every action, which measurably improves both accuracy on multi-hop tasks and interpretability of failures."*

## 7. Interview Q&A

**Q1: What problem does ReAct solve that pure Chain-of-Thought prompting doesn't?**
A: Chain-of-Thought lets a model reason step by step, but it's entirely closed-loop — the model reasons using only its parametric (trained-in) knowledge, with no way to fetch fresh, external, verifiable information. If that knowledge is wrong or stale, CoT just produces a confident, fluent, wrong answer. ReAct interleaves reasoning with actual tool calls, so each reasoning step is grounded in a fresh observation from the environment, and the model can course-correct when an observation contradicts its assumption.

**Q2: Walk through a multi-hop question and show how ReAct handles it differently than a single LLM call would.**
A: [Use the Oppenheimer/Nolan/London example above — director → birth city → population, where each search's result determines the next search's query, something a single non-agentic call cannot do without already knowing all three facts.]

**Q3: What's the biggest production risk of ReAct-style agents, and how do you mitigate it?**
A: Runaway loops — the model's own "am I done" judgment can fail to trigger, leading to excessive tool calls, cost, and latency. Mitigate with a hard max-iteration cap, explicit stopping criteria in the prompt, injecting a remaining-step budget into context, and programmatic repetition/loop detection that force-terminates near-duplicate action sequences.

**Q4: Why include the reasoning ("Thought") text at all — doesn't it just cost extra tokens?**
A: It does cost extra tokens (roughly doubling output length for reasoning-heavy trajectories), but ablations consistently show that removing the explicit reasoning step hurts action quality and error recovery — the reasoning text conditions the next action tokens, effectively acting as a plan the model then executes against. It's a token-cost-for-reliability tradeoff, and reliability usually wins outside of the most latency/cost-sensitive paths.

**Q5: How does ReAct recover when a tool returns an ambiguous or unhelpful result?**
A: Because the loop resumes with a fresh Thought after every Observation, the model can explicitly reason "this result doesn't answer my question" or "this is ambiguous/outdated," and issue a refined action — e.g., a more specific query — rather than being stuck with a bad result. This self-correction only exists because reasoning happens *between* the action and the next action, not just once at the start.

---

## 8. Summary Card

- **ReAct = Thought → Action → Observation, looped**, until the model itself decides to stop.
- Fixes CoT's blindness to the real world, and fixes plain tool-use's lack of an explicit reasoning trace.
- The Thought step isn't decorative — it decomposes problems, enables error correction, and conditions better actions.
- Biggest production risk: **unbounded loops** → always cap iterations and give explicit stop criteria.
- Cost: roughly n LLM calls for an n-turn trajectory, plus reasoning-token overhead on each.
