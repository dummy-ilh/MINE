# RAG Interview Prep — Day 15
## Citation & Faithfulness Enforcement at Runtime

---

## 🚀 Quick Summary

Faithfulness (from the evaluation curriculum) is usually discussed as something you *measure* after the fact — decomposing an answer into claims and checking each against retrieved context. Today is about the other half of the story: what you actually **build into the system at runtime** to make faithful, well-cited answers more likely to happen *in the first place*, rather than just detecting when they didn't. This spans prompt-level instructions, citation generation mechanisms, runtime groundedness verification as a guardrail (not just an eval metric), and how refusal behavior ("I don't know") gets taught and calibrated — because a well-calibrated refusal is often the single highest-leverage faithfulness intervention available.

**Think of it like the difference between grading a student's essay for citations after submission, versus teaching them good citation habits and giving them a citation-checking tool *before* they submit.** Post-hoc faithfulness evaluation (Module 7) is the grading. Today's topic is the habit-building and the pre-submission checking tool — the actual runtime mechanisms that make the graded outcome better in the first place.

---

## 🔑 Key Concepts

| Term | One-line definition |
|---|---|
| **Runtime faithfulness enforcement** | Mechanisms built into the generation pipeline itself to increase grounded, well-cited output — as opposed to measuring faithfulness after the fact |
| **Inline citation** | A citation marker (e.g., `[1]`) generated by the model as part of its output, pointing to a specific source |
| **Post-hoc attribution** | Generating the answer first, then separately verifying/attributing each claim back to source chunks in a following step |
| **Constrained decoding** | Restricting the model's output generation to conform to a required structure (e.g., forcing valid citation syntax) |
| **Refusal calibration** | Tuning a system's tendency to say "I don't know" so it neither over-refuses (unhelpful) nor under-refuses (hallucinates confidently) |
| **Groundedness guardrail** | A runtime check (often NLI-based) that verifies generated claims against context *before* the response is returned to the user |
| **Claim decomposition** | Breaking a generated answer into individual, independently-checkable factual claims |

**The key distinction to articulate in an interview:** Module 7's faithfulness metric answers "how well is my system doing, on average, across many responses" — a monitoring/evaluation question. Both matter, and they reinforce each other (a runtime groundedness guardrail's pass/fail decisions can even be logged and aggregated into an evaluation-time faithfulness signal), but they're solving different problems on different timescales.

# PHASE 2 — Deep Dive: Runtime Mechanisms

## 1. Prompt-Level Instructions (the cheapest, first line of defense)

**Mechanism:** explicit system-prompt instructions telling the model to (a) only use the provided context, (b) cite sources for claims, and (c) explicitly decline when the context doesn't support an answer — this is the direct runtime counterpart to Day 13's prompt template discussion, now viewed specifically through the faithfulness lens.

**Why this alone isn't sufficient (a common interview follow-up):** prompt instructions shape the model's *tendency*, not a guarantee — an LLM can still generate an unsupported claim despite being told not to, especially under ambiguous or partially-covered queries. This is why prompt instructions are described as the *first* line of defense, not the *only* one — they reduce the rate of faithfulness failures but don't eliminate the need for verification mechanisms further down the pipeline.

---

## 2. Citation Generation Approaches

### Approach A — Inline citations generated during generation

**Mechanism:** the model is instructed (via prompt, and ideally reinforced via fine-tuning — Day 1's "fine-tune for skill" pattern) to emit citation markers like `[1]` or `[source: doc_id]` directly as part of its generated text, referencing the `<source id>` tags established in the context (Day 13's prompt structure).

**Trade-off:** cheap (no extra model calls — citations come "for free" as part of the same generation pass), but citation *accuracy* is only as good as the model's tendency to correctly associate claims with the right source — a model can generate a plausible-looking citation marker next to a claim it actually drew from a *different* source, or from no source at all (a fabricated citation), which is arguably worse than no citation, since it creates false confidence in the answer's grounding.

### Approach B — Post-hoc attribution (verify after generation, before returning to user)

**Mechanism:** let the model generate its answer *without* worrying about citations during generation, then run a **separate verification pass** afterward: decompose the generated answer into individual claims, and for each claim, check (via NLI entailment classification or embedding similarity against the retrieved chunks) which source chunk(s) actually support it — attaching citations based on this verification, rather than trusting the model's self-reported citations.

**Why this is often more reliable than Approach A:** it decouples "does the model say this is cited" from "is this actually supported by the source" — directly addressing Approach A's fabricated-citation risk, since the citation is now assigned by an independent verification step rather than generated (and potentially hallucinated) by the same model that wrote the claim.

**Worked conceptual example:**
```
Generated answer (no citations yet): "AirPods Pro have 6 hours of
battery life and are covered by a 1-year warranty."

Claim decomposition:
  Claim 1: "AirPods Pro have 6 hours of battery life"
  Claim 2: "AirPods Pro are covered by a 1-year warranty"

Verification against retrieved chunks:
  Claim 1 → matches source chunk #1 (battery life doc) via NLI
            entailment → CITE [1], claim supported
  Claim 2 → NO retrieved chunk mentions warranty length at all →
            UNSUPPORTED, no citation available

→ Final response either flags Claim 2 as unsupported (triggering a
  runtime guardrail, see below) or the system regenerates the answer
  with an instruction to omit unsupported claims.
```

### Approach C — Constrained decoding for citation format

**Mechanism:** rather than relying purely on instructions and hoping the model complies, use constrained/structured decoding (forcing the model's output to conform to a specific grammar or schema, e.g., requiring every sentence to be followed by a valid citation token from a fixed set of available source IDs) to *guarantee* syntactic citation compliance.

**What this does and doesn't solve:** constrained decoding can guarantee the *format* is always correct (every claim has a syntactically valid citation marker) — but it cannot guarantee the citation is *accurate* (pointing to a source that actually supports the claim). Format compliance and factual correctness of the citation are separate problems; constrained decoding solves only the former, and still benefits from being paired with the post-hoc verification of Approach B for actual accuracy.

## Citation Approach Comparison Table

| | Inline (during generation) | Post-hoc attribution | Constrained decoding |
|---|---|---|---|
| **Extra latency/cost** | None (part of the same generation pass) | Moderate (extra verification pass, NLI/embedding checks) | Low (decoding-time constraint, not necessarily an extra full pass) |
| **Risk of fabricated citations** | Higher — model can cite the wrong or no real source | Low — citation is assigned by independent verification, not model self-report | Format guaranteed correct, but accuracy still unverified without pairing with post-hoc checking |
| **Guarantees syntactic format compliance?** | No | N/A (citations added after the fact) | Yes |
| **Best used** | As a baseline / cheap first pass | As a reliability upgrade, especially for high-stakes domains | Combined with post-hoc verification for both format guarantee and accuracy |

## 3. Runtime Groundedness Guardrails

**Mechanism:** before a generated response is returned to the user, run an automated groundedness check — essentially, run Module 7's faithfulness-measurement mechanism (claim decomposition + NLI/LLM-judge entailment checking) as a **live gate**, not just an offline eval metric. If the groundedness score falls below a threshold, trigger a fallback behavior (e.g., regenerate with stricter instructions, return a hedged/uncertain response, or explicitly say the system couldn't find sufficient grounded information) instead of returning the ungrounded response.

**Worked latency trade-off example:**
```
Base generation latency: ~800ms (typical for a moderate-length answer)

Runtime groundedness check (claim decomposition + NLI verification
against retrieved chunks, using a smaller/faster model than the
main generator): ~200-400ms additional

Total added latency for the guardrail: ~200-400ms, roughly a
25-50% increase over base generation latency alone
```
**Why this trade-off is often worth it:** for high-stakes domains (medical, legal, financial, or any domain where a confidently-wrong answer carries real cost), the latency cost of a runtime groundedness check is usually justified by the risk reduction — this is a direct engineering expression of the same principle behind Module 7's emphasis on faithfulness as the primary hallucination-detection metric, just applied as a live gate instead of an offline measurement. For lower-stakes, casual-use applications, this added latency/cost may not be justified, and prompt-level instructions plus post-hoc attribution (cheaper) might be considered sufficient.

> **Why This Matters callout:** If asked "how would you prevent a RAG system from hallucinating in production, not just detect it after the fact," the strong answer describes this runtime guardrail pattern explicitly — running a lightweight version of the faithfulness check *before* the response reaches the user, with a defined fallback behavior for failures, rather than only relying on post-hoc monitoring/evaluation to catch problems after they've already been shown to users.

---

## 4. Refusal Calibration — Teaching "I Don't Know"

**Why this is arguably the highest-leverage single intervention:** a well-calibrated refusal directly prevents the worst failure mode in RAG — a confident, fluent, wrong answer — by having the system recognize when its retrieved context genuinely doesn't support a good answer, and saying so instead of guessing. This directly serves the "no good answer exists" eval slice from Module 7's golden eval set discussion.

**How refusal behavior is actually built (multiple layers, not one trick):**
1. **Prompt-level instruction** — explicit instruction to decline when context is insufficient (cheap, first line of defense, same caveat as above: a tendency, not a guarantee).
2. **Fine-tuning on refusal examples** — training data specifically containing (query, insufficient-context, correct-refusal-response) examples, teaching the model this behavior as a learned skill rather than relying purely on prompt compliance (tying back to Day 1's framing: fine-tuning is well-suited to teaching *behavior*, and refusal calibration is exactly that kind of behavior).
3. **Confidence/groundedness thresholding** — using the runtime groundedness guardrail's score (mechanism #3 above) as an explicit signal: if grounding confidence falls below a calibrated threshold, trigger a refusal response rather than returning the low-confidence answer as-is.

**The calibration trade-off (a real tuning problem, not a fixed setting):**
- **Threshold too aggressive (refuses too often):** the system becomes unhelpful, declining to answer questions it actually could have answered reasonably well — a real usability cost.
- **Threshold too lenient (refuses too rarely):** the system produces confident wrong answers on genuinely unsupported queries — the exact hallucination risk refusal calibration exists to prevent.
- Like chunk-size tuning (Day 3) and semantic cache thresholds (Day 14), this requires empirical validation against a golden eval set that specifically includes the "no good answer exists" slice (Module 7 §7.6) — you cannot calibrate refusal behavior well without deliberately testing on cases where refusal is the *correct* answer, not just cases where answering is correct.

---

## Attribution Granularity — Sentence-Level vs. Claim-Level

**The distinction:** citing at the *sentence* level (each generated sentence gets one citation) is simpler to implement but coarser — a sentence can contain multiple distinct factual claims, only some of which might actually be supported by the cited source. Citing at the *claim* level (decomposing sentences into individual atomic factual assertions, each independently verified and cited) is more precise but more expensive to compute and can produce a more fragmented-looking citation style.

**Worked example illustrating the gap:**
```
Generated sentence: "AirPods Pro have 6 hours of battery life and
are IPX4 water resistant, though this rating does not cover
submersion."

If cited at the SENTENCE level with one citation [1]: this implies
the entire sentence, including the submersion caveat, is supported
by source [1] — but what if the submersion caveat actually came
from a different source [2], or wasn't retrieved at all?

If cited at the CLAIM level: "AirPods Pro have 6 hours of battery
life [1] and are IPX4 water resistant [1], though this rating does
not cover submersion [UNVERIFIED]." — this correctly flags that the
submersion caveat specifically lacks a verified source, even though
the rest of the sentence is well-grounded.
```
**Why it matters in practice:** sentence-level citation can create a false impression of uniform groundedness across a sentence that actually blends supported and unsupported content — claim-level attribution is more faithful to what Module 7's faithfulness metric is actually measuring (individual claim-level entailment), but the finer granularity costs more computation (more individual verification checks) and can make responses look more fragmented/hedgy to end users, a real UX trade-off worth naming.

# PHASE 3 — Interview Q&A Practice Set

*(Answers are separated below each question — cover them and self-test first.)*

---

**Q1 (Easy — conceptual).** What's the difference between measuring faithfulness (Module 7) and enforcing faithfulness at runtime (today's topic)?

<details>
<summary>Show answer</summary>

Measuring faithfulness is a post-hoc, typically aggregate evaluation activity — assessing how well the system performs on average across many responses (or eval set queries), useful for monitoring and comparing configurations. Enforcing faithfulness at runtime means building mechanisms directly into the live generation pipeline — prompt instructions, citation generation, groundedness guardrails, refusal calibration — that shape or check each individual response before it reaches the user, aiming to prevent or catch faithfulness failures in real time rather than only detecting them afterward in aggregate.
</details>

---

**Q2 (Easy — conceptual).** Why is prompt-level instruction alone (e.g., "only use the provided context") not sufficient to guarantee faithful output?

<details>
<summary>Show answer</summary>

Prompt instructions shape the model's tendency toward faithful behavior but don't guarantee it — an LLM can still generate unsupported claims despite being explicitly instructed not to, particularly for ambiguous queries or partially-covered topics. This is why prompt instructions are treated as a first, cheap line of defense, not a complete solution — additional mechanisms like post-hoc verification or runtime groundedness guardrails are needed to actually catch failures that prompt compliance alone doesn't prevent.
</details>

---

**Q3 (Medium — conceptual).** Why can post-hoc attribution (verify-then-cite) be more reliable than having the model generate inline citations directly?

<details>
<summary>Show answer</summary>

Inline citations generated directly by the model are self-reported — the model can produce a plausible-looking citation marker next to a claim without that citation actually being accurate, essentially a fabricated citation, which can be worse than no citation since it creates false confidence in the answer's grounding. Post-hoc attribution decouples the claim-generation step from the citation-assignment step: citations are assigned by an independent verification process (checking each decomposed claim against retrieved chunks via NLI or embedding similarity) rather than trusted from the same model that generated the claim, directly reducing the fabricated-citation risk.
</details>

---

**Q4 (Medium — conceptual).** What does constrained decoding guarantee about citations, and what does it NOT guarantee?

<details>
<summary>Show answer</summary>

Constrained decoding can guarantee syntactic format compliance — e.g., every claim is followed by a validly-formatted citation token referencing an available source ID, enforced at the decoding level rather than relying on the model choosing to comply. It does NOT guarantee that the citation is factually accurate — i.e., that the cited source actually supports the claim it's attached to. Format correctness and citation accuracy are separate problems; constrained decoding solves only the former and should ideally be paired with post-hoc verification to address the latter.
</details>

---

**Q5 (Medium — reasoning).** Why is refusal calibration described as potentially the highest-leverage single faithfulness intervention?

<details>
<summary>Show answer</summary>

The worst RAG failure mode is a confident, fluent, wrong answer — a well-calibrated refusal directly targets this by having the system recognize when retrieved context genuinely doesn't support a good answer and explicitly declining, rather than generating a plausible-sounding guess. Since this failure mode is arguably the most damaging one (worse than an obviously-hedged or clearly-incomplete answer), directly reducing its occurrence through calibrated refusal has an outsized impact on overall system trustworthiness compared to incremental improvements elsewhere in the pipeline.
</details>

---

**Q6 (Hard — calibration trade-off reasoning).** Your team calibrates refusal behavior and finds the system now refuses to answer 30% of queries in production, even though a manual review suggests only about 8% of queries genuinely lack sufficient context. What does this suggest, and how would you fix it?

<details>
<summary>Show answer</summary>

This suggests the refusal threshold is calibrated too aggressively — the system is over-refusing, declining to answer a meaningful number of queries it actually could have answered reasonably well from available context, which is a real usability cost even though it avoids the opposite (hallucination) risk. To fix this, I'd revisit the calibration process: validate the groundedness-confidence threshold against a golden eval set (Module 7 §7.6) that includes both genuinely-answerable and genuinely-unanswerable queries in known proportions, adjusting the threshold to better match the manually-reviewed 8% true refusal rate rather than the current 30%, and consider whether the underlying groundedness-scoring mechanism itself is being overly conservative (e.g., an NLI-based check that's too strict about what counts as "supported") independent of the threshold itself.
</details>

---

**Q7 (Hard — system design synthesis).** Design the citation and faithfulness enforcement strategy for a medical-information RAG system, where wrong answers carry serious real-world risk, and justify the latency/cost trade-offs you'd accept.

<details>
<summary>Show answer</summary>

Given the high stakes, I'd layer multiple mechanisms rather than relying on any single one: (1) strong prompt-level instructions as a baseline, cheap first line of defense; (2) fine-tuning on refusal examples specifically, since medical queries with insufficient context should reliably trigger a "consult a professional" style response rather than a confident guess — this is exactly the kind of behavior Day 1 argues fine-tuning is well-suited for; (3) post-hoc attribution rather than trusting inline citations, given the fabrication risk is unacceptable in this domain; (4) a runtime groundedness guardrail gate before any response is returned — accepting the ~200-400ms additional latency, since for a medical-information use case, the risk-reduction value clearly outweighs a latency cost of that magnitude; (5) claim-level (not sentence-level) attribution granularity, since medical statements often carry important caveats/conditions that sentence-level citation could misleadingly imply are uniformly well-supported. I'd calibrate the refusal threshold using a golden eval set deliberately weighted toward hard, ambiguous, and unanswerable medical queries, accepting a somewhat higher refusal rate than a lower-stakes application would tolerate, since in this domain, an unhelpful-but-safe refusal is a much better failure mode than a confident-but-wrong medical claim.
</details>

# 🧠 Gotchas — Common Mistakes Recap

- ❌ Treating prompt-level "only use context" instructions as sufficient on their own — they reduce, but don't eliminate, faithfulness failures.
- ❌ Trusting model-generated inline citations without independent verification — a real fabricated-citation risk.
- ❌ Assuming constrained decoding solves citation accuracy — it only guarantees format, not correctness.
- ❌ Treating faithfulness measurement (Module 7, aggregate/offline) and faithfulness enforcement (today, per-response/runtime) as the same thing, or as substitutes for each other.
- ❌ Calibrating refusal thresholds without a golden eval set that specifically includes unanswerable/insufficient-context queries — you can't tune this well without deliberately testing the refusal-correct cases.
- ❌ Defaulting to sentence-level citation without recognizing it can misleadingly imply uniform groundedness across a sentence with mixed supported/unsupported claims.

---

# 📌 Cheat Sheet (Day 15)

**Layered defense (no single mechanism is sufficient alone):** prompt instructions (cheap, first line, tendency not guarantee) → citation generation (inline = cheap but fabrication-risky; post-hoc attribution = more reliable, extra verification pass; constrained decoding = guarantees format only) → runtime groundedness guardrail (live gate before returning to user, ~200-400ms typical added latency, justified for high-stakes domains) → refusal calibration (arguably highest-leverage single intervention, needs golden-eval-set-based threshold tuning).

**Citation approaches:** inline (fast, fabrication risk) vs. post-hoc attribution (verify-then-cite, decouples claim generation from citation assignment, more reliable) vs. constrained decoding (format guarantee only, pair with post-hoc for accuracy).

**Refusal calibration:** teach via prompt + fine-tuning + groundedness-threshold gating together. Threshold too aggressive = unhelpful over-refusal; too lenient = confident hallucination. Requires a golden eval set including genuinely-unanswerable queries to calibrate correctly.

**Attribution granularity:** sentence-level (simpler, can misleadingly imply uniform support) vs. claim-level (more precise, more expensive, matches what Module 7's faithfulness metric actually measures).

**Golden interview line:** *"Faithfulness measurement tells you how the system is doing on average; faithfulness enforcement is what you build into the pipeline so any individual response is more likely to be grounded in the first place — and refusal calibration is usually the single highest-leverage piece, because a well-calibrated 'I don't know' prevents the worst failure mode: confident, fluent, wrong."*
